# 改這段字（retext）— 設計

2026-11-19。MVP，先玩玩看。

## 為什麼

改網站上的字，本質是「找到那個字串、換掉」。交給 AI 做，錢不是花在取代，是花在找位置、
來回好幾趟、以及每開一次對話的固定成本。所以這種修改不經過 AI：在網頁上選字、右鍵、打新的字，
收件服務自己去原始碼找到並換掉。零 token。

## 目標 / 不做

- 做：改畫面上看得到、原始碼裡也原樣存在的字；多處修改累積起來一次送出（一次 commit、一次 push、一次部署）。
- 不做（這一版）：CSS、跨元素的選取、程式拼出來或資料庫來的字、放棄還沒送出的修改、HTML entity 對應。
- 不可以：改到別人還沒 commit 的工作、把會弄壞程式的符號塞進原始碼、任何網頁都能偷偷叫它改檔。

## 做法（Jeff 選的）

考慮過三種：

1. **右鍵改字，累積後一次送出** ← 選這個。改五處只部署一次，入口沿用強力右鍵。
2. 右鍵改字，改一個推一個。最簡單，但連改會連續部署。
3. 整頁編輯模式，點哪改哪。最順，之後做 CSS 也長在這上面，但要多做很多；文字版用順了再升級。

「哪個網站對應哪個專案」不做設定檔（Jeff 明講：到處都能按，不是自己的站改不了就好）。
選單項目在所有網頁都出現；服務拿那段字去 `RETEXT_ROOTS`（預設：這個 repo 的上一層資料夾）
底下每個 git repo 找。改成功一次之後記住「這個網域 → 這個 repo」，之後只找那個 repo，找不到才再全部找。

## 行為

- `POST /retext { text, to, url, pick? }`
  - 一處命中 → 直接換，回 `done` 與「還沒送出」的數量。
  - 多處命中（≤12）→ 回 `choose` 與清單（repo、檔、行號、那一行），帶 `pick` 再送一次。超過 12 → `toomany`。
  - 沒命中 → `notfound`；腳本把一句給 AI 的指令放進剪貼簿。
  - 新的字帶進原本沒有的 `< > { } \` " ' \\` 或換行 → 422，不改。
  - 那個檔有不是這個工具造成的未 commit 修改 → 409，不改。
- `POST /retext/submit { url }`：那個網域對應的 repo，把改過的檔做成一個 commit（`chore: 網頁改字 N 處`）再 `git push`。
  push 失敗時修改留在「還沒送出」，可以再按一次。
- `GET /retext/pending?host=`：還沒送出幾處。
- 三條路都要金鑰；POST 只收 JSON（跟 `/drop` 同一道防線）。

比對：網頁會把換行與縮排顯示成一個空白，所以任何一段空白都對得上任何一段空白。
只找 git 有追蹤的文字類檔案（html、js、ts、tsx、vue、md、json…），跳過 `.min.*` 與超過 1MB 的檔。
git worktree（`.git` 是檔案）不算一個專案，避免同一份程式出現兩次。

狀態放 `~/.power-right-click/retext.json`（`PRC_HOME` 可改）：網域對應、還沒送出的清單。

## 腳本這邊

右鍵選單多一項「改這段字」→ 對話框（原本／改成）→ Enter 送出。成功後把畫面上的字當場換掉，
左下角出現「已改 N 處，還沒送出 [送出]」。只有改過字的網域，載入頁面時才會去問還有沒有沒送出的。

## 我自己定的（Jeff 沒講，可以改）

- 送出前不跳 diff：每一處都是親手改的。
- 多個 repo 都有同一段字時用清單挑，挑過就記住。
- commit 訊息格式與「會弄壞程式的符號」清單。

## 驗證

- `npm test`：服務端 9 個情境（單一命中、跨行、多處挑選、找不到、危險符號、髒檔、送出、push 失敗、金鑰）。
- 腳本：無頭瀏覽器實跑（選字 → 右鍵 → 改 → 畫面變 → 送出 → 遠端有 commit），還沒放進 `npm test`。
